# Snapshot provenance profile — ONT-047

`eventcore-provenance-v1` version `1.0.0` explicitly selects draft
`org.0al.events.core@0.2.0`. Its [descriptor](../profiles/eventcore-provenance-v1.json),
IR SHA-256 and source digest are pinned in the validator. Each graph and authority
input carries the exact profile pin, including the descriptor's byte hash.
This adds origin/admission checks to the bounded event graph checks; it is not a
proof backend or an attestation of physical truth.

## Compatibility and selection

The [legacy eventcore-v1 contract](../README.md), its 0.1.0 YAML/IR/SDK, generated
consumer shapes, report fields and limitation fixture remain frozen. The default
CLI/library profile is still eventcore-v1. Supplying a 0.2.0 IR without explicitly
selecting the new profile fails the pin check. No existing graph/report is upgraded,
migrated, relabeled or reinterpreted. A graph contains one vocabulary revision.

The [0.2.0 package](../../packages/events-core/versions/0.2.0/README.md) adds three
origin classes and four relations. Generated object schemas alone do not enforce
origin admission. Use the selected instance validator and its separate authority input.

## Three distinct claims

1. **Source presence:** a SourceAssertion or capture artifact is named. This is
   a declaration in untrusted data; it does not confirm origin or truth.
2. **Origin confirmation:** an explicitly selected trusted authority input admits
   this exact graph's snapshot-origin pair under a scoped capability grant.
3. **Factual truth:** whether the claimed complete state actually occurred. This
   profile does not decide that question, authenticate identity/signatures, fetch
   artifacts, validate extraction relevance or establish source completeness.

The caller must choose the authority input from trusted storage independently of
the graph. Never accept an authority file selected/generated by an untrusted graph
as a new source of permission. A caller controlling both inputs can make false
declarations. The validator checks the supplied authority contract, not the
trustworthiness of the caller. Hashes bind bytes, not truth or immutable history.
The prototype has no authority revocation service or cryptographic receipt format.

## Typed snapshot origin

Every StateSnapshot has exactly one of these alternatives. Every origin belongs
to exactly one snapshot and originKey is unique across origin types in the graph.
This applies to empty, nonempty and currently unreferenced snapshots.

| Snapshot relation / origin class | Required declaration | Confirmation capability |
|---|---|---|
| snapshotSourceOrigin / SourceSnapshotOrigin | originKey, extractionMethod and one or more originCitesAssertion links; cited sourceDigest has sha256 format | confirm-source |
| snapshotDirectOrigin / DirectObservationOrigin | originKey, observerKey, artifactRef, sha256 artifactDigest, nonnegative observedAt and clockKey | confirm-observation |
| snapshotOperatorOrigin / OperatorSnapshotOrigin | originKey, operatorKey and nonblank rationale; explicitly uncited | supply-operator-state |

Identity and textual origin fields must be nonblank. A direct capture used as a
record's before/after snapshot must match its intervalStart/intervalFinish and
clockKey. The profile checks declared identity/time, not authenticity or that a
frame actually depicts the state. Source hash format is checked; source bytes
are not fetched or compared. Operator supply requires confirmation by the same
operatorKey, with capability in the exact scope and projection. Reviewing a
source/interpretation is not any of these capabilities.

## External authority input

`SnapshotProvenanceAuthority` uses
`ontology.specgraph.io/snapshot-authority/v1alpha1` and contains:

- `profilePin`, `graphKey`, `revisionKey` and `graphSHA256` of the **exact graph bytes**;
- unique `grants`: authorityKey, allowed capabilities, scopeKeys and projectionKeys;
- unique `confirmations`: snapshotId, its actual originId, authorityKey and nonblank rationale;
- unique `enrichments`: candidateId, recordId, authorityKey and nonblank rationale.

Capabilities are confirm-source, confirm-observation, supply-operator-state and
enrich-candidate. Grants are explicit finite lists without wildcards. One
confirmation is required per snapshot; unrelated/stale/wrong-origin confirmations,
duplicate identities, unknown fields and unsupported capabilities fail closed.
All inputs use the same bounded UTF-8/no-BOM/unique-key parser. The report hashes
both raw inputs. Identity authentication is explicitly false.

Any byte change, including whitespace or role-only edits, invalidates the old
authority binding and requires explicit reconfirmation. This conservative v1
choice binds the complete declaration and its links without inventing a canonical
subgraph/claim digest. The validator never generates or refreshes confirmations.
Fixtures are synthetic caller inputs, not real observations or signed approvals.

## Admissible enrichment

A candidate can remain source-only indefinitely: absent/unknown/partial observations
need no complete snapshots, record or Delta. The source-only fixture passes with
snapshotCount 0 and confirmationStatus no-snapshots. Validation does not create
states, infer missing facts, infer negative facts or synthesize a Delta.

For every candidateEnrichedByRecord link:

- The existing episode, reference, registry, interval and projection checks apply.
- Both complete snapshots already require confirmed typed origin.
- A separate enrichment entry needs enrich-candidate capability for both snapshots'
  scopes/projections. Snapshot confirmation alone does not authorize promotion.
- A known candidate observation must retain the identical snapshot. Every supplied
  partial proposition/polarity pair must be retained in the corresponding complete
  state. Unknown/absent observations remain on the original candidate; any newly
  supplied record states are explicit additional declarations.
- candidateResolvedAsInterpretation must derive from such an explicitly enriched
  candidate-record link. Proposed/reviewed status is never admission authority.

An exact empty Delta is allowed for explicitly supplied equal complete states
with admitted origins, including empty sets. This validates finite-set arithmetic;
it does not establish that the physical world was unchanged. Omission of a Delta
remains distinct from an empty Delta. A later alternative account requires explicit
new declarations/decisions rather than overwriting known/partial evidence.

## CLI and reports

```sh
ontologyc validate-instances graph.json \
  --ontology-ir SPECS/ontology/packages/events-core/versions/0.2.0/generated/ontology.normalized.json \
  --profile eventcore-provenance-v1 \
  --provenance-authority trusted-authority.json --out report.json

ontologyc export-instance-contract \
  --ontology-ir SPECS/ontology/packages/events-core/versions/0.2.0/generated/ontology.normalized.json \
  --profile eventcore-provenance-v1 --out consumer-contract
```

The new library parameters are profile and provenanceAuthorityPath; both remain
optional for legacy callers. Legacy profile plus authority input is rejected.
Export rejects an authority input because export grants no instance admission.

The new report adds profilePin and provenance: confirmationStatus
(confirmed-under-supplied-authority, no-snapshots or not-confirmed),
authorityInputSHA256, authorityAuthenticationVerified false, sourceTruthVerified
false and snapshotCount. Its existing authority flags keep sourceTruthVerified,
causationVerified and responsibilityVerified false. A failed graph gets no positive
confirmation status even when some declarations were valid. Reports are deterministic
and bound to bytes; they are not authorization for unrelated graphs or future versions.

## Regression evidence

[Static fixture cases](../../fixtures/instance-graphs/provenance/cases.json) cover
source-only, three admitted origin types, known empty Delta, missing/ambiguous
origins, citation without confirmation, missing source link, operator capability
and identity, wrong scope, stale bytes, wrong receipt targets, duplicate receipts,
invalid capture boundary and unauthorized enrichment/resolution. Mutation tests
also exercise known/partial preservation, orphan origins, unsupported authority
fields, blank rationales and malformed authority encoding. The original v1
limitation remains an expected pass in the separate legacy gate.

Run tools/snapshot-provenance-smoke.sh using the built CLI; it validates staged
YAML, deterministic package/consumer baselines and the static cases. Swift tests
exercise real CLI/library admission, failed reports and IR/pin tampering. TypeScript
checks generated origin object shapes and consumer types; it is not a second
cross-input authority verifier. No NormLab exporter/deployment changes are included.
